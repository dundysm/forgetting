forgetting · how this was made

an AI agent's memory, replayed inside a real brain

Every bright point is one token slot of an LLM serving engine's memory, the KV cache, replaying a real benchmark run event by event. Give the engine enough memory and its brain glows with recall. Starve it and it forgets each conversation just before that conversation comes back.

The experiment

vLLM 0.31.0 serving Qwen3-4B-Instruct on one NVIDIA A40. 16 scripted agent sessions take turns, 12 turns each. Every turn re-sends the session's whole history (about 3,000–3,400 tokens), with a 0.5 s "tool call" pause before the next turn and 4 requests in flight. Prefix caching lets a turn reuse the KV cache of its own previous turn, if that cache is still on the GPU.

The only thing that changes between the two brains is how much GPU memory the KV cache gets: 4.5 GiB holds 32,768 tokens, and 10 GiB holds 72,816. The 16 sessions' histories need 54,173. At 4.5 GiB the pool is big enough for every request that is actually running, but not for all the idle sessions waiting their turn. LRU eviction always throws out the session that has waited longest, which, because the sessions take turns in a circle, is exactly the one that is up next. There were zero preemptions in every run: all the forgetting happens to sessions that are idle.

Full method, pre-registration and raw data: github.com/dundysm/inference-under-pressure.

Which point on the cortex a memory slot sits on is an artistic choice, made once: each block's 16 tokens form one grain of cortex, and the grains are chained nearest-neighbour across the surface, so block b sits next to block b+1. vLLM's free queue tends to hand out runs of neighbouring blocks, so a session's memory lands as one territory; under pressure, as the LRU recycles slots, you watch that territory fragment. The fragmentation is real; the map is not. The anatomy carries no data. Everything that moves does.

How the replay works, and how it was checked

vLLM reports, per request, how many prompt tokens came from the cache. It does not log which GPU block was evicted when. To animate each block, tools/replay.py replays vLLM v1's block manager over the measured request timeline, using the real start time, time to first token, end time and size of every request:

Prompt blocks are allocated at request start, and decode blocks at the first token. At request end, all of a request's blocks go to the tail of an LRU free queue in reverse order. New allocations evict from the head. Which blocks are reused comes straight from the measured cached-token counts. The replay decides only when everything else is evicted.

The check: every block the engine actually reused must still be in the replayed cache at that moment. It was, for every reuse in all 15 runs, with 0 inconsistencies. On its own, without being told the measured reuse, the replay predicts the measured cached tokens exactly for 192/192 requests at every budget from 2.5 to 6 GiB, and 168–171/192 at 8 and 10 GiB. Each miss there is one 16-token block, the one holding the end of the previous prompt plus the model's reply. In those requests the next scripted prompt happened to start with the same tokens the model had generated.
